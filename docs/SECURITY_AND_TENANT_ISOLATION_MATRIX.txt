1. ZERO-TRUST ARCHITECTURAL FOUNDATION
--------------------------------------------------------------------------------
The IINSHA AI-BOS system enforces a strict Defense-in-Depth, Zero-Trust model
operating across three distinct security boundaries:
1. Edge Perimeter (Cloudflare Pages Functions): Request method validation, CORS origin
   whitelist, CSRF protection, and body schema parsing.
2. Application Logic & Auth Gateway: HMAC-SHA256 signed JWTs with strict expiration,
   TOTP multi-factor verification, and role-based hierarchy enforcement.
3. Database Engine (PostgreSQL / Supabase): Mandatory Row Level Security (RLS) on all
   tables, SECURITY INVOKER views, tenant-scoped schemas, and double-entry invariants.

3. DATABASE ROW LEVEL SECURITY (RLS) POLICIES
--------------------------------------------------------------------------------
All production tables enforce Row Level Security. Direct cross-tenant data access
is mathematically blocked at the Postgres engine level.

Table: ibos_tenants
- Isolation Key: id = auth.jwt() ->> 'tenant_id'
- SELECT: Allowed for tenant members (auth.uid() in tenant_users)
- INSERT: Blocked for non-owners; Service Role only
- UPDATE: Allowed only for tenant owners (role = 'owner')
- DELETE: Blocked in production (soft-delete only)

Table: ibos_profiles
- Isolation Key: id = auth.uid()
- SELECT: Own profile only, or tenant admins within same organization_id
- INSERT: Bound to authenticated user identity (id = auth.uid())
- UPDATE: Own profile fields only; role and hierarchy mutations restricted
- DELETE: Blocked

Table: ibos_orders
- Isolation Key: organization_id = (auth.jwt() ->> 'org_id')::uuid
- SELECT: Members can view orders matching their organization_id
- INSERT: Automatically populates organization_id from authenticated session
- UPDATE: Restricted to order owners (status transitions governed by state machine)
- DELETE: Strictly forbidden (Audit log retention invariant)

Table: payment_transactions
- Isolation Key: organization_id = (auth.jwt() ->> 'org_id')::uuid
- SELECT: Scoped to tenant organization; sensitive PAN/card data never stored
- INSERT: Restricted to authorized payment adapter routines
- UPDATE: Blocked; transactions are immutable ledger records
- DELETE: Strictly forbidden

Table: agent_executions
- Isolation Key: tenant_id = (auth.jwt() ->> 'tenant_id')::uuid
- SELECT: Scoped to executing tenant
- INSERT: Scoped to executing tenant; requires valid task DAG token
- UPDATE: Agent step progression permitted only for active runner session
- DELETE: Blocked; execution logs are permanently retained

Table: ibos_coupons & coupon_redemptions
- Isolation Key: Global validation, per-user single redemption
- SELECT: Active coupons visible; redemption records scoped to user_id
- INSERT: Authoritative redemption verified via atomic stored procedure
- UPDATE: Redemptions cannot be revoked or altered
- DELETE: Blocked

Table: audit_logs
- Isolation Key: organization_id
- SELECT: Tenant owners and auditors only
- INSERT: System triggers and security invoker routines only
- UPDATE: Strictly blocked at engine level (Append-only invariant)
- DELETE: Strictly blocked at engine level (Tamper-proof invariant)


4. ADVERSARIAL THREAT MODELING AND MITIGATION EVIDENCE
--------------------------------------------------------------------------------
Threat 1: Cross-Tenant Data Access (BOLA / IDOR)
- Vector: Tenant A injects Tenant B's order UUID into /api/orders/get.
- Defense: Database RLS automatically adds 'WHERE organization_id = :tenant_id' to
  the executed AST. Zero rows returned.
- Test Evidence: scripts/test_tenant_isolation_adversarial.mjs -> PASS (Status: EXPECTED_SECURITY_DENIAL)

Threat 2: Admin Session Forgery & Signature Tampering
- Vector: Attacker crafts a fake JWT claiming role='owner' and hierarchy_level=1.
- Defense: HMAC-SHA256 signature verification uses secret stored exclusively in
  Cloudflare Functions environment. Constant-time signature comparison eliminates timing attacks.
- Test Evidence: scripts/test_admin_auth_security.mjs (Test 7) -> PASS (HTTP 401 FORGERY_REJECTED)

Threat 3: Token Expiration & Replay
- Vector: Attacker re-uses an expired admin token or a stolen refresh token.
- Defense: Expiration timestamp (exp) strictly enforced; refresh tokens require re-authentication.
- Test Evidence: scripts/test_admin_auth_security.mjs (Tests 8 & 1) -> PASS (HTTP 401 TOKEN_EXPIRED)

Threat 4: Payment Webhook Replay & Race Conditions
- Vector: Attacker re-posts a valid payment confirmation payload multiple times to credit balance twice.
- Defense: Webhook idempotency ledger checks provider transaction ID in an atomic transaction;
  duplicate payloads are rejected with HTTP 409 Conflict.
- Test Evidence: scripts/ci_evidence_runner.mjs (payment_replay_concurrency) -> PASS

Threat 5: Password Cracking & Rainbow Table Attacks
- Vector: Offline dictionary or brute-force attack on database hashes.
- Defense: Adaptive PBKDF2 with 100,000 iterations, unique 16-byte cryptographically secure salt,
  and constant-time hash comparison loop.
- Test Evidence: scripts/test_admin_auth_security.mjs (Test 12) -> PASS
